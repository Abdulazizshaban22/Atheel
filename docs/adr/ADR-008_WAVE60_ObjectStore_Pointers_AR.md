# ADR-008

## العنوان
Wave60 نقل مخرجات التصدير إلى Object Store وإرجاع مؤشرات فقط

## السياق
في Wave57 فصلنا خدمة التصدير exports-svc. في Wave58 أضفنا Service Outbox لضمان موثوقية الإرسال وإعادة المحاولات، وفي Wave59 جعلنا القناة عبر Nest ClientProxy.

لكن بقيت مشكلة أساسية: مخرجات التصدير هي ملفات كبيرة PDF و PPTX و ZIP. نقل هذه الملفات داخل الرسائل عبر base64 يضغط الناقل ويزيد الذاكرة ويعرضنا لحدود حجم الرسائل.

## القرار
اعتماد نمط:
1) exports-svc تولد الملفات ثم تكتبها في Object Store
2) ترجع للـ API مؤشرات فقط object { provider, key }
3) الـ API يقوم بتحويل هذه المؤشرات إلى Attachments (أو يمكن لاحقًا جعل Attachment نفسه مؤشرًا دون نسخ)
4) إضافة Idempotency على مستوى exports-svc عبر Inbox مبنية على messageId

## الأسباب
- تقليل حمل الرسائل والناقل
- تقليل الذاكرة في API (التخلص من base64 الضخم)
- جعل المنظومة قابلة للتوسع عند ملفات كبيرة
- دعم لاحق سهل لـ S3/MinIO بدون تغيير منطق الأعمال

## النطاق
هذه الموجة تقدم Object Store محلي افتراضيًا عبر نظام ملفات المشروع، مع واجهة قابلة للاستبدال لاحقًا بسواقات S3/MinIO.

## البدائل التي تم رفضها
1) الإبقاء على base64 داخل الرسائل
سبب الرفض: لا يتوسع ويزيد المخاطر التشغيلية

2) تحويل كامل إلى S3/MinIO مباشرة مع SDK
سبب التأجيل: نحتاج أولًا تثبيت العقد والواجهة وتدفقات التشغيل، ثم يتم تبديل السواقة لاحقًا دون لمس الدومين

## تبعات القرار
- إضافة متغيرات بيئة جديدة
- إضافة createFromFilePath في AttachmentsService
- exports-svc تكتب ملفات إضافية للـ Inbox (نتيجة الرسالة)
